Job Tracker Spec

Emily Ruth · October 27, 2026

This spec turns the Job Tracker PRD into testable requirements, acceptance tests and a prioritized backlog for the engineering team. This doc is the source of truth: the spec changes first, then the code.

ConventionsData modelRequirementsAcceptance testsDesign constraintsBacklogOpen questions

How to use this spec

  • Requirement IDs: AREA-n (for example, STG-2). Every test and task cites one.
  • Requirement format: WHEN [trigger], THE SYSTEM SHALL [behavior].
  • Test format: Given / When / Then, one test per requirement at minimum.
  • Done means: the task's tests pass and nothing in the regression list breaks.
  • Scope: the tracker app. Vetting runs in Claude and writes its results to the tracker; the VET requirements define that contract. Out of scope: multi-user accounts, production hosting, and the AI making final decisions.

Data model

Three entities. Every record carries id, version and updatedAt for safe merging (SYNC).

EntityFields
Jobtitle, company, link, posted date, date applied, date rejected, interviewing (bool), follow-up log, interview log, reply log, due date, review-site ratings and counts (2 sites), recommend %, excitement rating, general notes, vetting output
Contactname, company, phone (international), business email, personal email, LinkedIn, reply log
Companyname, rating, latest vetting date, vetting notes
  • Logs are lists of {date, note} entries; tables show the newest date.
  • Company links to jobs and contacts by exact name (see CO-4).

Design constraints

Rules for every change.

  • One HTML file, no build step. Keep the app a single self-contained file.
  • Local first. Browser local storage is the base; cloud sync through Claude Artifacts is optional.
  • One source of truth for stages. All stage moves (STG-1 to STG-4) go through one function. No stage logic elsewhere.
  • User edits win. Never overwrite a newer user edit (SYNC-1, SYNC-2).
  • Small changes. One task per change, its tests updated in the same change.
  • Spec first. A behavior not in this spec gets added here before it is built.
  • Keep the demo working. demo.emilyruth.me runs the same code with fictional data.

  • Stage moves. (STG-1 to STG-3)
  • Due dates and close-out suggestions. (REM-1 to REM-3)
  • Company creation, rename, delete, merge and rating roll-up. (CO-1 to CO-4)
  • Timestamped saves, merge by newest and version checks. (SYNC-1, SYNC-2)
  • Vetting write-back with gates, threshold and 60-day reuse. (VET-1 to VET-5)
  • JSON export. (BAK-1)
  • Weekday digest. (DIG-1)

Open questions

  • Which hard gates besides contract roles belong in VET-1?
  • Should CO-4 stay exact-match, or add fuzzy matching to cut duplicates?
